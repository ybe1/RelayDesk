# Ch06：正式分流器、订单选择与退款申请

日期：2026-10-02。状态：分段方案获同意，书面spec自审完成，待用户审阅；尚未实施。

## 1. 目标、范围和已确认决策

将Ch05占位的指代消解与意图分类升级为正式Workflow节点，在同一聊天入口支持多轮指代、话题切换、核心售后查询扩写和用户选单恢复。

技术保持FastAPI、SQLAlchemy/MySQL、LangChain、LangGraph/AsyncSqliteSaver、现有Milvus混合检索和重排，聊天上游保持当前配置（目前deepseek-v4-pro）。不引入服务、分类训练、跨会话记忆，不接真实订单或退款系统。

用户已确认：

- 通用政策FAQ直接检索，不强迫选订单；订单级退款/售后进入确定性子流程。
- 缺订单时用官方interrupt/Command恢复，不猜订单；新问题使旧待选流程失效。
- 等待用户不消耗处理时长；已消耗token、工具和模型次数不重置。
- 用户确认提交后MySQL保存演示退款申请，不实际退款，不承诺到账时间，重复点击幂等。
- 前端订单卡片/退款表单按Vibe实现；后端代码TDD，Prompt/数据用标注评估替代实现镜像测试。

## 2. 主流程与固定路由

主流程：当前消息与有限同会话历史 → 指代消解/口语改写 → 意图识别 → 固定分流。

| 意图/请求范围 | 出口 |
| --- | --- |
| 物流、订单 | 现有主力Agent，自主调用既有工具 |
| 商品咨询、通用政策FAQ | 单查询检索 → 置信度闸 → Agent回答 |
| 订单级退款退货、售后 | 订单槽位 → 查订单 → Query扩写 → 多查询政策检索 → 置信度闸 → Agent判断 |
| 投诉 | 固定安抚与独立转人工/工单选项；保留Ch05确认规则 |
| 闲聊 | 固定话术；明确的独立问候白名单继续零模型调用 |
| 其他 | 固定范围说明，请用户描述客服相关需求，不调用业务工具 |

通用政策FAQ范围在消解节点输出显式请求范围标记，由代码决定是否需要订单；分类器仍只判断“要干什么”，不追问、不输出执行动作。

退款/售后子流程的订单结果与政策证据在Agent前准备完毕。Agent判断订单适用性、必要条件或需要进一步确认的信息；它不决定是否省略查订单/查政策，也不自行执行退款或创建申请。物流仍可在退款之后的新轮正常分流。

## 3. 指代消解与口语归一

一次LLM调用同时处理指代与轻量改写，输入只含当前原话、当前会话近期完整轮次和可溯源的订单上下文。历史按完整用户轮次裁剪，工具申请与结果不能拆开；不查询其他会话。

结构化结果包含完整question、reference_status（resolved/clear/ambiguous）、请求范围（general/order_specific）、order_id和订单来源（current/history/none）。这些是消解节点内部字段，不加入意图JSON。

- 原问题完整、表达已明确：question与原话相同，不进行修辞改写。
- “它能退吗”且历史唯一明确提到订单1001：补全成订单1001是否支持退货。
- 历史有两单且不能唯一确定：reference_status=ambiguous，order_id为空，不擅自挑最近出现的数字。
- 输出订单号仅接受当前用户明确订单引用、当前会话已确认的选单或结构化工具结果。历史助手普通文字不是可信订单凭据；输出必须与服务端提取的来源集合匹配。
- 禁止补造商品属性、订单状态、收货时间、退款原因。无法完成消解时保留原问题及未确定标记，订单级请求显示选择器，其余澄清留给Agent。

近期历史固定最多保留6个完整用户轮次，并复用现有token裁剪；超大旧工具结果继续按请求保守预算删除完整旧轮，当前轮不拆分。不新增摘要或长期记忆策略。

## 4. 意图Prompt和模型策略

选择集合是物流、订单、商品咨询、退款退货、售后、投诉、闲聊、其他。JSON严格只有intent和confidence；confidence必须是有限数值且在[0,1]，不接受字符串/布尔值/额外字段/非法标签。Prompt枚举定义，附物流与订单、退款与维修、投诉与抱怨、闲聊与怪问题、话题切换的边界few-shot。用户要求指定标签不能覆盖系统分类规则。

默认用现有聊天大模型。大模型质量用标注集实测，不因模型名称宣称已达标。成本模式默认关闭，配置小模型名称后才启用，沿用相同聊天上游和凭证；小模型置信度低于可配置阈值时升级大模型一次。初始阈值0.75，评估时检查误判与升级比例，不把该分数当已校准概率。

低置信度不是立即归其他：成本模式先升级；最终仍拿不准才其他。默认大模型模式不重复调用同一模型赌答案。小模型非法JSON可升级一次；大模型非法JSON安全兜底并记录原因，网络错误报告暂不可用，不能伪称用户属于其他意图。

采用上游支持的JSON结构化模式并做Pydantic验证，保留原始usage结算。实际接口若不支持预定模式，先查官方文档；技术矛盾无法按既定上游解决时停止询问用户，不自行换供应商。

## 5. 订单槽位与可恢复暂停

订单选择器候选由服务端演示目录提供，不由LLM造卡片；每个匿名用户在本系统演示约定下获得固定候选1001/1002/1003，页面明确“演示订单”。候选与query_order/query_logistics共用一致性快照，不表示真实公司账号订单归属。

为政策判断在mock快照补充演示商品名称、品类、收货天数（未收货为null）等必要事实，与现有状态关联；商品当前完好程度等无法从订单确定的条件不伪造，由Agent说明条件或澄清。订单/物流仍不建表。

订单级退款/售后明确带订单号时正常查该演示订单；需要点选时只接受该轮实际发出的候选。模型没有凭据时不能自行调用某订单来填槽。

新增POST /api/chat/selection流式恢复接口，body包含user_id、conversation_id、turn_id、selection_id、order_id。服务端检查会话归属、当前pending轮次、选单标识、候选集合与会话占用。越权403、不存在404、过期/重复恢复/占用409；格式错误422。有效请求向同thread_id执行Command(resume=...)，随后沿既有SSE输出，恢复节点后再查订单。

interrupt单独放在无模型、无写库副作用的选单节点。模型解析、选项生成等节点在暂停前已checkpoint，不在恢复时重复运行。State持久化原/规范问题、指代来源、意图/置信度、pending选择和预算快照，不保存客户端、数据库session或模型对象。

SSE新增order_selection事件，带演示订单卡片和待选标识。用户等待时结束当前HTTP流并释放占用，State保留interrupt；完成帧区分waiting与answered。前端不把等待渲染为最终回答，不挂完成反馈。刷新同一会话可通过只读待选状态接口恢复卡片，不触发模型或查订单。

恢复时重建runtime context，沿用累计预算，用量与已活动处理时长不重置，用户等待不计入120秒。pending用户发送新消息时服务端终结旧待选轮次，失效旧selection_id，并显式启动新轮；旧卡片后续点击409。没有自动替用户点击、选默认订单或提交退款。

正常waiting不走Ch05异常取消终结逻辑；真正断连仍停止活动执行、等待已开始的账本写入、补齐悬空工具结果。同会话并发请求继续互斥。成功重复选单不重复查订单，客户端显示已选择。

## 6. 确定性查单与多查询检索

确定性订单节点复用query_order与ToolExecutor，每次实际调用含重试计入工具预算，标准assistant申请和tool结果写消息流水。一次确定性查单后Agent复用该结果，不能为相同目的重复查单。

扩写模型输出严格为{"queries":[...]}, 1至3条非空查询；保留规范原问为第一条，其余可覆盖退货资格、政策限制、申请步骤等不同角度。去掉重复和超长查询，不扩张用户未请求的业务范围、不编造事实或退款原因。最多3条是已介绍的控制成本建议。

只有订单级退款/售后扩写。简单FAQ不扩写，不把扩写写知识库。

复用Ch04召回路径：每条dense/BM25各Top50并RRF融合；问题向量可批量取得，各路候选按chunk_id合并。合并后用规范原问题统一调用一次现有reranker，取Top10，保持首尾证据编排。合并候选采用各查询公平轮取上限50，避免首查询占满；按chunk_id去重，不直接比较不同查询的融合分数。

规范问题由消解节点已提供，通过现有understood_query接口传递；每个扩写分支不再重复调用Ch04Query理解模型。分类过滤继续使用现有白名单规则，不能由扩写字符串拼任意Milvus表达式。

所有必选查询成功才形成证据结果；一条上游失败可在其既定有限重试内恢复，仍失败则整体检索兜底，记录实际错误，不能假装完成多路召回。无命中/弱证据复用置信度闸和低置信度池，保存用户原话；不进入Agent硬编退款结论。保留Ch05简单分数闸已知局限，不宣称本章实现正式语义充分性闸。

## 7. Agent判断、退款表单与MySQL

Agent拿到规范问题、可信订单快照和政策证据，只评估本单是否支持申请及需要满足的条件；输出内部结构化判断eligible/ineligible/needs_review并保留引用编号，面向用户继续流式回答。未知条件不得补成已满足，needs_review转条件说明或需求澄清，不冒称审批通过。退款原因不在对话前置追问，统一留在申请表单中自选；必要的其他适用条件澄清留给Agent。

仅退款请求且结论支持申请时发出refund动作建议，不自动提交；维修类售后不误发退款表单。证据不足、禁止退货或必要事实无法判断时不给自动退款申请入口，保留人工核实/工单建议。模型推荐动作不能绕过服务端对本轮订单、政策证据和判断结构的核验。

复用chat_action_offers，action ENUM新增refund，其defaults存服务端绑定的订单号、演示判断/证据快照；同会话/轮次/action唯一约束沿用。模型不能自造offer_id。已有handoff/ticket行为不变。

新增refund_requests（InnoDB/utf8mb4）：

| 字段 | 约束/用途 |
| --- | --- |
| id | BIGINT UNSIGNED自增主键 |
| application_no | VARCHAR(32)，唯一演示申请号 |
| offer_id | VARCHAR(64)，非空、唯一，外键chat_action_offers.offer_id，幂等键 |
| conversation_id | BIGINT UNSIGNED，非空，外键conversations.id |
| order_id | VARCHAR(64)，非空；订单不建表，无订单外键 |
| reason | ENUM('不喜欢/不需要','商品质量问题','商品与描述不符','错发/漏发','其他')，非空 |
| status | ENUM('submitted')，默认submitted，只表示申请保存 |
| is_mock | TINYINT(1)，默认1，服务端固定演示标记 |
| snapshot | JSON，服务端保存订单/判断/证据溯源快照 |
| created_at | DATETIME默认CURRENT_TIMESTAMP |

会话和创建时间建普通索引。check/apply迁移先核现有结构，不删表、不清历史；offer ENUM变更保留已有值。SQLAlchemy与实施DDL一致。

新增POST /api/chat/actions/refund：仅接受user_id、conversation_id、offer_id和固定reason。订单和金额不由客户端改填；本章不计算或执行资金动作。核归属、锁offer、验证有效退款建议，事务内写申请，commit后返回“演示申请已提交”和申请号。相同offer/原因重复返回同一申请；同offer修改原因返回409，不覆写原申请。

表单显示订单、固定原因下拉和演示说明；用户确认才请求API。取消不落申请，双击提交不会重复写库，失败保留重试机会。不把申请成功说成退款成功，不承诺到账时间、不自动改会话已转人工。

## 8. 预算、错误、可观测与兼容

默认保留Ch05上限：6模型调用、5工具实际执行、12000累计输入/输出token、120秒活动处理时长。正常核心路径预计消解1、意图1、扩写1、Agent决策1、最终生成1；成本升级最多再1，共6。检索分支不额外LLM改写；已有订单传入Agent。

预算包含失败请求，暂停后累计；embedding/rerank继续另记次数/时间，不能称免费。复杂澄清/额外业务调用仍受限制。如果评估表明正常场景在此预算内走不通，停止向用户提出具体调参证据，不擅自提高。

日志打印原/规范问题、reference_status、意图/置信度、模型层级/是否升级、路由、selection等待/恢复、查询数、候选去重计数、节点trace、停止原因和usage。不得打印密钥。用户问题属于会话日志原文，不发无关第三方。

新节点仍用现有SSE delta/tool_status/citations/actions；保留引用弹窗、反馈、投诉双按钮。workflow_summary新增规范问题/意图置信度等可核验诊断字段，不给用户暴露内部JSON。历史已完成会话正常启动新轮；历史Ch05未完成线程不自动重放写动作。

云上游故障、非法JSON、弱证据、等待用户和预算停止必须可区分。网络故障不归类其他，有限重试耗尽明确服务暂不可用；不改变Clash设置或供应商。

## 9. 标注评估、测试和交付

Prompt/数据验证：固定不少于40条单轮题（含8类、边界、歧义、怪问题、提示注入）和至少6组多轮会话，每组至少4轮，覆盖物流→退款→物流、多订单指代、完整问题透传、通用政策FAQ与订单级诉求区分。人工预标intent、是否应改写、规范问题关键事实、订单来源和路由；不以模型自己生成标签作ground truth。

门槛：正常上游返回的意图JSON在标注评估中100%符合两字段契约；故意注入非法输出的后端测试必须安全兜底、不得执行工具，不能把兜底计为正确分类。单轮意图准确率至少95%，验收指定的多轮切换和指代例全通过；完整清晰问题不改写；歧义不猜；怪问题归其他。若上游失败，报告blocked/error不能算通过；无需重跑Ch04的300题。

扩写评估覆盖核心退货/维修、简单FAQ不扩、无事实添油、queries单字段、长度/数量/去重。模型判断用符合条件/不支持/信息不足三类订单与政策标注样例，检查引用与退款入口。

后端TDD覆盖槽位来源校验、暂停/进程重开/预算继承、越权、并发选单、重复恢复、过期卡片、新消息取消等待、tool申请结果配对、多路召回合并及错误、退款表单事务幂等。现有全仓回归和MySQL迁移check为必需门槛。

前端Vibe浏览器验证：缺订单退款出现卡片；点选后节点继续并流式回答；刷新恢复pending；旧卡片失效；退款原因下拉、取消零写库、确认一条申请、重复确认无新增；现有引用/反馈/投诉交互保留。不套前端正式brainstorm/TDD/code-review。

交付包含启动/迁移/单条演示/离线及真实评估命令、逐例报告、全仓测试结果、spec/plan路径和dev-notes/ch06.md。每完成阶段立即补四项记录，不在收尾集中追记。默认延续Native实施方式，实施前仍需用户审阅书面spec与计划。
