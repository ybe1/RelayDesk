MewHelp 电商智能客服项目报告

面向商品咨询、订单物流与售后服务的智能客服系统

摘要　MewHelp 以电商客服为应用场景，将大语言模型、知识库检索与业务工具结合，提供多轮问答、订单查询、售后处理及知识持续更新能力。系统采用 FastAPI 与 LangGraph 构建服务和工作流，以 MySQL 保存业务记录，以 Milvus 支撑混合检索，并通过人工审核与效果评估形成改进闭环。目前已完成主要原型功能及阶段验收，尚需进一步接入真实业务、完善身份权限与部署能力。

一 项目背景与建设目标

电商客服既需要回答退换货、运费、产品说明等重复性问题，也需要根据具体订单处理物流和售后请求。传统固定规则难以覆盖自然语言表达，直接使用大模型又可能出现答案缺乏依据、混淆订单信息或擅自执行操作等问题。因此，本项目围绕“回答有依据、操作可控制、问题可追踪”三个目标设计系统。

项目希望让用户在一个聊天入口中完成咨询与业务请求：通用政策从知识库获得依据，订单问题通过工具查询，涉及写入的操作先展示预览并取得确认。对于无法可靠回答的问题，系统保留原问题和证据，供运营人员审核与补充知识，从而减少同类问题反复无法解决的情况。

三 建设范围与阶段划分

项目按章节逐步演进：第一至二章建立流式对话、结构化提取和工具调用；第三至四章建设知识库与混合检索；第五至六章引入多步 Agent、意图路由与售后流程；第七至八章完善上下文管理和可扩展工具系统；第九章接入可观测性、人工审核与数据反馈闭环。第十章已形成主题分类设计及实施计划，尚未完成代码实现。

五 关键技术与实现机制

5.1 混合检索与证据约束

知识原文先写入 MySQL，再按同一知识片段 ID 写入 Milvus。检索结合向量相似度和 BM25 关键词匹配：向量检索处理“邮费”和“运费”这类语义表达差异，关键词检索补充商品型号、条款等精确匹配，再通过重排选择更相关的证据。

生成前，系统综合最高重排得分、有效证据数量、排名分差及关键条款信号计算置信度，权重分别为 0.5、0.2、0.2 和 0.1。阈值由标注样本校准，再结合证据自评判断是否足以支持回答。证据不足时进入拒答与知识缺口记录流程，避免仅凭模型已有知识给出平台政策。

5.2 工作流与多步工具调用

LangGraph 将处理过程组织为明确节点。知识问题先检索，订单与物流问题进入工具路径；涉及连续查询时，Agent 可以依据前一个工具结果决定下一步。执行预算限制工具次数、模型调用、累计 token 与耗时，使异常循环能够停止。问候等确定性场景可直接返回固定回复，减少不必要调用。

5.3 多轮会话与上下文管理

系统保存会话原文，并在模型输入侧按预算组织近期历史、较早历史与摘要。较远内容逐步压缩为摘要段，后台摘要采用追加方式，避免不断重写已有记录。该机制旨在兼顾多轮问答中的订单与诉求回忆，以及模型输入容量限制；当前范围是同一会话，不包含跨会话用户画像。

5.4 工具权限与写入控制

工具系统统一接入内置工具与独立 MCP 服务，本地权限策略对未登记工具默认拒绝。只读工具的临时网络错误可有限重试，创建工单超时不会自动重试。建单前展示固定参数的预览，确认时由服务端使用预览记录执行；重复确认保持幂等，取消不写入工单。工具审计保留来源、参数、状态与耗时，便于定位问题。

订单处理需要可靠的对象来源。系统优先使用用户明确提供的订单号，或与工具申请对应且返回 ID 匹配的业务查询结果。对于缺少对象、指代不清或条件未知的问题，先补充信息，避免将助手先前生成的文字当作订单事实。

6.2 工单确认与提交

工单流程把“表达诉求”和“正式提交”分开：系统先收集问题描述，展示预览，再依据用户确认创建记录。确认后的页面反馈工单结果，便于用户知道请求是否完成。下图来自浏览器合成响应验收，用于说明交互表现。

七 知识反馈与运营闭环

客服系统上线后的知识质量需要持续维护。MewHelp 将低置信度问题、证据自评不足和用户负反馈汇入知识缺口池，对相近问题标准化与归并。审核人员可以查看原始问法及当轮证据，批准答案或驳回记录；批准后，系统创建待索引知识片段，增量更新当前混合索引，并在后续问答中使用。

为便于判断知识缺口来源，系统区分“未检索”“检索成功但无结果”和“检索得到证据”三种快照状态；网络超时等运行故障不直接当作知识不足。索引写入成功后再回填原文状态，中断后可恢复，降低业务库与检索索引不同步的风险。

九 当前不足与后续改进

业务与权限接入仍需完善。订单、商品、物流及部分售后结果属于演示数据，匿名用户标识尚不能替代生产登录鉴权。下一步应接入真实业务接口，建立用户、订单与操作权限的对应关系，并补充接口异常和越权场景验证。

部署与数据一致性存在边界。当前检查点方案适用于本机单实例，同一会话的多进程处理需要额外协调；MySQL 业务账本与 SQLite 图状态之间不承诺跨库原子提交。生产化时应完善并发控制、恢复机制、监控告警和备份方案。

效果仍需真实业务验证。现有评估主要基于指定语料和标注集，尚无充分证据量化真实人工工作量、用户满意度或平均响应时间的改善。后续应扩充长尾问题与对抗样本，并在真实流量中观察拒答率、解决率和调用成本。

主题分类进入下一阶段。第十章拟建设 17 类问题分类，采用 AutoDL 云端训练与本地批量推理，帮助识别高频主题和服务薄弱环节。该模块目前仅完成设计与实施计划，后续还需完成数据标注、训练、逐类评估及后台接入。

十 项目结论

MewHelp 已形成覆盖咨询、业务查询、售后交互和知识更新的智能客服原型。其主要价值在于将生成式问答嵌入可检查、可确认、可追踪的流程，并用人工审核和持续评估支撑知识维护。现阶段成果适合功能展示和技术验证；下一步应围绕真实业务接入、权限体系及生产部署继续完善。
