# Ch02 Function Calling 工具链 · 开发过程追记

> 每阶段记录：用户关键原话 / 关键产出 / 用户拒绝或纠偏 / 翻车与返工。

## 阶段 1：需求澄清与设计（2026-09-19）

**用户关键原话：**“工具链要长在客服聊天本身”；“只做单轮调用”；“建表和测试数据初始化也由你在实施阶段完成，现在先澄清需求、完成设计，不要收到 SQL 就立即执行建表”。

**关键产出：**检查现有 `/api/chat`、聊天页、内存历史与提示词；用 Context7 核对 FastAPI、SQLAlchemy、LangChain、DeepSeek 文档；写出 Ch02 spec 与 plan。用户确认服务端生成数字会话 ID、浏览器保存匿名用户 ID 的方案。设计规定本轮只执行第一个工具申请，消息协议仍为其余申请配对未执行结果。

**用户拒绝或纠偏：**无。用户明确要求聊天页实施阶段采用 Vibe Coding，不套 brainstorm、TDD、code review 流程。

**翻车与返工：**无。本阶段未执行建表、启动容器、灌数据或改业务代码。

## 阶段 2：数据库基建与持久化（2026-09-19）

**用户关键原话：**“建四张表灌测试数据”；“SQLAlchemy 模型要与它保持一致”；“商品、订单、物流走工具内 mock，不建表”。

**关键产出：**新增 MySQL 8.4 Compose、四表 DDL、SQLAlchemy 映射与短会话工厂；实现会话归属检查、消息顺序写读、FAQ 字面 LIKE、工单与会话状态同事务更新。FAQ 种子首次插入 2 条，再运行插入 0 条。数据库映射与仓储集成测试 3 个通过。

**用户拒绝或纠偏：**无。

**翻车与返工：**初次容器初始化的 MySQL 客户端把中文 SQL 当错误字符集读取，中文 ENUM 值乱码，工单状态更新失败。DDL 加 `SET NAMES utf8mb4`，改用新卷 `mysql_ch02_utf8` 重新初始化；旧卷保留。复测 3 个通过。

## 阶段 3：业务工具与聊天接入（2026-09-19）

**用户关键原话：**“工具链要长在客服聊天本身”；“只做单轮调用”；“最终回答仍逐 token 流式吐出，工具执行那一段先推个状态帧”。

**关键产出：**五个 LangChain `@tool` 工具、注册与参数校验、5 秒超时和只读工具重试；聊天服务选工具后最多执行第一个，为其余申请回传未执行结果，保存工具申请与结果，再流式输出最终回答。聊天页改为使用服务端会话 ID，并在当前气泡显示工具徽章。提示词和请求 Schema 均先写失败测试再实现；聊天页按 Vibe Coding 直接改。完整测试 38 项通过。

**用户拒绝或纠偏：**无。

**翻车与返工：**开发环境一度找不到 `docker` 命令，实际 Docker Desktop 已安装并运行；用安装目录内的完整路径验证客户端与引擎均为 29.8.0。工具状态曾以字符串包含 `"error"` 判断，边界测试发现正常结果可能误判，改为解析结果 JSON 的顶层键。

## 阶段 4：真实模型标注样例（2026-09-19）

**用户关键原话：**“订单 1001 的物流到哪了”；“退货政策是什么”；“邮费是多少”，第三句漏召回是预期结果。

**关键产出：**使用当前 `.env` 的 `deepseek-v4-pro` 与本地 MySQL 运行 `uv run python -m scripts.eval_ch02`：物流问题调用 `query_logistics`，返回订单 1001 的随机演示轨迹；退货政策调用 `query_faq` 并命中种子；邮费问题也调用 `query_faq`，结果为空且模型说明未查到。三条脚本断言均通过，每条会话中恰有一次工具结果。此漏召回留给 Ch03。Chrome 无界面浏览器实际点击聊天页：物流问题显示 `query_logistics` 徽章，流式回答由中途 50 字增加到最终 102 字，证明气泡保持逐段更新。

**用户拒绝或纠偏：**无。

**翻车与返工：**直接运行脚本文件时 Python 找不到仓库 `app` 包，改用模块形式 `python -m scripts.eval_ch02` 后通过。Windows 终端输出中文曾乱码，脚本显式配置 stdout UTF-8 后复跑三条样例均通过且中文可读。页面失败态样式最初未识别后端的 `error` 阶段，补全映射。

## 阶段 5：后端评审与断流修复（2026-09-19）

**用户关键原话：**“聊天记录（含工具调用与结果）落 conversations/messages 表”。

**关键产出：**后端代码评审发现 1 个 Important：工具申请已落库、状态帧已发出，但客户端此时断开会留下无配对工具结果的历史。先写断流后关闭生成器的两条失败测试，再将工具结果写入提前到完成状态帧之前，并在生成器退出时为未完成申请补写 `interrupted` 工具消息。5 条聊天服务测试、全套 40 条测试通过；三条真实模型样例复跑通过。评审者复核确认此 Important 已解决。

**用户拒绝或纠偏：**无。聊天页仍按用户指定的 Vibe Coding 例外，不纳入后端代码评审。

**翻车与返工：**首次实现只覆盖正常消费完整 SSE 流，遗漏了工具状态帧处断连的持久化边界；评审指出并经先红后绿修复。
